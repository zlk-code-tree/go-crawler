# 千川消耗接入及盈亏推送方案

## 一、现状分析

### 1.1 已具备的能力

| 能力 | 现状 | 覆盖范围 |
|------|------|----------|
| 千川消耗数据拉取 | ✅ 已接入，每日04:37自动拉取，存储到 `qianchuan_ad_report` | 所有已授权千川广告主 |
| 订单数据 | ✅ 抖店API拉取 + 快手/视频号Excel导入 | 三平台全覆盖 |
| 佣金计算 | ✅ `FinanceCommissionService` 支持按投手/部门/公司维度 | 三平台全覆盖 |
| 日聚合任务 | ✅ 每日02:00自动聚合到 `finance_daily_stats` | 账号→投手→部门→公司 |
| 利润公式 | ✅ `OrderService.Stats()` 已有完整公式 | 仅抖音订单维度 |
| 账号管理 | ✅ `account` 表，含 operator/company_id/department_id | 三平台 |
| 投手管理 | ✅ `trader` 表，支持角色区分(投手/运营)，关联账号 | - |
| 消息通知 | ✅ WebSocket实时推送 + `system_notification` 表 | 仅平台内 |

### 1.2 核心缺口

1. **千川广告主与内部账号未关联** — `qianchuan_ad_report.advertiser_id` 与 `account` 表无映射关系，广告消耗无法归属到具体运营/投手
2. **广告消耗未进入聚合链路** — `finance_daily_stats.ad_cost_amount` 字段存在但始终为 0，聚合SQL未JOIN千川报表
3. **缺少外部推送通道** — 没有企业微信/飞书 webhook 集成，无法主动推送盈亏数据
4. **缺少多周期盈亏视图** — 仅有单日聚合，无7日/15日/30日滚动窗口

### 2.2 第一步：千川消耗接入（补全映射关系）

#### 2.2.1 问题

当前 `qianchuan_ad_report` 表只有 `advertiser_id`（千川广告主ID），与内部 `account` 表（达人账号）无关联。广告消耗数据无法归属到具体运营/达人。

#### 2.2.2 映射关系分析

根据抖音规则：
- **单一主体（公司）下**：1 个抖音号只能在 1 个千川账户搭建推广计划 → **一对一**
- **多主体情况下**：同一个抖音号可以分别在多个主体下的千川账户搭建计划 → **一对多**

因此映射关系是 **`(达人账号, 所属公司) → 千川广告主ID`**，需要独立的映射表而非在 `account` 表加单字段。

#### 2.2.3 方案：新建千川广告主映射表

```sql
CREATE TABLE IF NOT EXISTS account_qianchuan_mapping (
  id BIGINT AUTO_INCREMENT PRIMARY KEY,
  account_id INT NOT NULL COMMENT '内部账号ID，关联account.id',
  company_id BIGINT NOT NULL DEFAULT 0 COMMENT '所属公司ID，关联sys_company.id',
  qianchuan_advertiser_id BIGINT NOT NULL COMMENT '千川广告主ID',
  qianchuan_advertiser_name VARCHAR(200) DEFAULT '' COMMENT '千川广告主名称（冗余，方便查看）',
  created_at DATETIME DEFAULT CURRENT_TIMESTAMP,
  updated_at DATETIME DEFAULT CURRENT_TIMESTAMP ON UPDATE CURRENT_TIMESTAMP,
  UNIQUE KEY uk_account_company (account_id, company_id),
  KEY idx_advertiser_id (qianchuan_advertiser_id)
) COMMENT '内部账号与千川广告主映射表';
```

**映射关系：**

```
account_qianchuan_mapping
  ├── account_id      → account.id（内部达人账号）
  ├── company_id      → sys_company.id（所属公司/主体）
  └── qianchuan_advertiser_id → qianchuan_ad_report.advertiser_id
```

**数据流变化：**

```
之前: qianchuan_ad_report (advertiser_id) → 无法关联 → 只能查总消耗
之后: qianchuan_ad_report (advertiser_id) 
      → account_qianchuan_mapping (qianchuan_advertiser_id)
      → account (account_id) 
      → trader_account_relation → trader → department → company
```

#### 2.2.4 管理员绑定流程

1. 在账号管理页面增加"千川广告主绑定"入口
2. 展示当前 OAuth 授权下可用的千川广告主列表（从 `qianchuan_token.advertiser_ids` + Ocean Engine API 获取名称）
3. 运营/管理员选择账号 + 公司 → 绑定对应千川广告主ID
4. 支持"自动匹配"：根据千川广告主名称模糊匹配账号名称（如 "利云文化官方旗舰店" → account_name 包含 "利云文化"）

#### 2.3.3 SQL查询逻辑

```sql
-- 按运营查询今日消耗
SELECT 
    t.id AS trader_id,
    t.name AS trader_name,
    COALESCE(SUM(qar.stat_cost), 0) AS ad_cost
FROM trader t
JOIN trader_account_relation tar ON t.id = tar.trader_id
JOIN account a ON tar.account_id = a.id
JOIN account_qianchuan_mapping aqm ON a.id = aqm.account_id AND a.company_id = aqm.company_id
JOIN qianchuan_ad_report qar ON aqm.qianchuan_advertiser_id = qar.advertiser_id
WHERE qar.stat_datetime = CURDATE()
  AND t.id = ?
GROUP BY t.id, t.name;
```

### 2.4 第三步：自动计算内部员工/团队今日消耗/佣金/盈亏

#### 2.4.1 盈亏计算公式（沿用现有逻辑）

```
定价总额         = Σ(有效订单 product_price × product_num)
货款(成本)       = Σ(有效订单 base_price × product_num)
留底(3%)         = 定价总额 × 0.03
小店服务费(2%)   = 定价总额 × 0.02 (仅抖音)
退款成本         = Σ(无效且已发货订单 base_price × product_num)
佣金扣除(0.5%)   = (定价总额 - 留底 - 货款) × 0.005

广告消耗         = Σ(关联千川广告主 stat_cost)

净利润           = 定价总额 - 货款 - 留底 - 退款成本 - 小店服务费 - 佣金扣除 - 广告消耗
```

#### 2.4.2 改造日聚合任务

在现有 `FinanceAggregateService.DailyAggregateJob()` 中增加广告消耗关联：

**现有逻辑（finance_aggregate.go:168-209）：**
- `queryPlatformOrders` 按 `talent_id` 分组查询订单
- `aggregateByShop` 通过 `talent_id` → `account.uid` 找到账号
- 写入 `finance_daily_stats`，但 `ad_cost_amount` 字段始终为 0

**改造方案：**

在 `aggregateByShop` 阶段，增加广告消耗查询：

```go
// 在 aggregateByShop 中，对每个 account，查询关联的千川消耗
func (s *FinanceAggregateService) getAdCostByAccount(ctx context.Context, accountId int, companyId int64, date string) float64 {
    row, err := g.DB().GetOne(ctx, `
        SELECT COALESCE(SUM(qar.stat_cost), 0) AS cost
        FROM qianchuan_ad_report qar
        JOIN account_qianchuan_mapping aqm ON aqm.qianchuan_advertiser_id = qar.advertiser_id
        WHERE aqm.account_id = ? AND aqm.company_id = ? AND qar.stat_datetime = ?
    `, accountId, companyId, date)
    if err != nil {
        return 0
    }
    return row["cost"].Float64()
}
```

然后将结果赋值给 `OrderStatItem.AdCostAmount`。

#### 2.4.3 新增实时盈亏计算接口

由于日聚合任务是凌晨跑的，当天的数据需要实时计算。新增一个 service 方法：

```go
// GetRealtimeProfit 实时计算当日盈亏（按trader/dept/company维度）
func (s *FinanceCommissionService) GetRealtimeProfit(
    ctx context.Context, 
    traderId int64, 
    deptId int64, 
    companyId int64,

```

逻辑：
1. 查询当天三张订单表的有效订单 + 成本
2. 查询当天千川广告消耗（通过 account 映射）
3. 按公式计算盈亏
4. 支持 trader/dept/company 三种维度聚合

## 五、风险与注意事项

1. **千川API限流** — Ocean Engine API 有调用频率限制，实时查询需加缓存（Redis或内存缓存，TTL 5分钟）
2. **广告主ID映射准确性** — 一个达人可能有多个千川广告主，需支持一对多映射（可在 account 表用逗号分隔多个ID，或新建映射表）
3. **数据一致性** — 日聚合在凌晨2点，千川拉取在4:37，聚合时前一天广告消耗可能还未拉取。建议调整时序：千川拉取 → 5:00 聚合任务
4. **飞书/企微消息限流** — 飞书机器人消息频率限制为 20条/分钟，企微为 20条/分钟，推送频率不高不会触发
5. **今日数据实时性** — 白天查询"今日"数据需要实时计算，不能依赖凌晨的预聚合表。实时计算的SQL性能需要关注（建议对 `pay_finish_time`、`stat_datetime` 加索引）

## 六、后续扩展建议

1. **ROI 分析** — 在盈亏基础上增加 ROI = 净利润 / 广告消耗，帮助投手优化投放策略
2. **异常告警** — 当日广告消耗超过阈值时自动推送告警（如单计划消耗 > 5000元）
3. **多群推送** — 不同公司/部门推送到不同的飞书群/企微群
4. **数据对比** — 推送内容增加环比/同比数据（如"较昨日 +12.3%"）
