# 财务管理功能逻辑与计算口径

> 本文根据当前后端与财务管理前端代码整理，用于产品、财务、运营和研发共同核对系统现行口径。
>
> 整理日期：2026-07-20

## 1. 功能范围

当前财务管理包括三个主要模块：

1. **达人佣金**：按公司、部门、投手和账号查看订单、佣金及利润。
2. **千川消耗**：按组织、店铺、主体、达人等维度查看千川广告消耗。
3. **千川计划**：按店铺、抖音号、商品、计划逐级查看消耗、订单归因和利润。

三个模块顶部汇总尽量采用统一的抖音订单经营口径，但千川计划筛选结果和计划明细利润仍存在部分差异，详见“已知口径差异”。

## 2. 订单统计口径

### 2.1 有效订单

满足下列任一条件的订单计入有效订单：

- 订单状态属于 `已发货、待发货、已完成、3、2、5`，且售后状态不属于 `6、7、11、12、29`；
- 订单状态属于 `已关闭、已取消、4`，但售后状态属于 `27、28、51`。

公式表示：

```text
有效订单 =
  （正常订单状态 AND 非无效售后状态）
  OR
  （关闭/取消订单状态 AND 售后已关闭状态）
```

### 2.2 无效订单

售后状态属于以下状态的订单计入无效订单：

```text
6、7、11、12、29
```

### 2.3 退款成本订单

只有满足以下条件的订单才计算退款成本：

```text
售后状态 = 12 AND send_time 不为空
```

即：退款成本是“已发货后发生退款的订单所对应的商品成本”，不是全部退款金额。

## 3. 达人佣金计算

### 3.1 定价总额

```text
定价总额 = Σ（有效订单商品单价 × 商品数量）
```

字段来源：

```text
order_info.product_price × order_info.product_num
```

### 3.2 商品货款

```text
商品货款 = Σ（商品基础成本价 × 有效订单商品数量）
```

成本匹配关系：

```text
订单 seller_code → 商品 goods_code → 商品 base_price
```

如果订单没有匹配到商品成本，统一抖音快照中按 `0` 计算。因此商品成本资料缺失会造成货款偏低、佣金和利润偏高。

### 3.3 留底

```text
留底 = 定价总额 × 3%
```

结果按金额四舍五入保留两位。

### 3.4 小店服务费

抖音订单：

```text
小店服务费 = 定价总额 × 2%
```

其他平台当前按 `0` 处理。

### 3.5 页面“达人佣金”

当前财务管理页面中的达人佣金计算公式为：

```text
达人佣金
= 定价总额
- 商品货款
- 留底
- 小店服务费
```

展开后：

```text
达人佣金
= 定价总额
- 商品货款
- 定价总额 × 3%
- 定价总额 × 2%
```

化简为：

```text
达人佣金 = 定价总额 × 95% - 商品货款
```

> 注意：该字段实际更接近“扣除货款、留底和平台服务费后的可分配毛利”，并不等同于从抖店结算账单读取的实际达人佣金。

系统虽然保存了外部达人的线上佣金率和线下佣金率，但当前财务管理“达人佣金”汇总没有使用这两个佣金率计算。特殊佣金率目前主要用于抖音订单页的订单归类、佣金率展示和外部达人线下佣金统计，具体规则见下文。

### 3.6 佣金扣除

利润计算中另有一项佣金扣除：

```text
佣金扣除 = 定价总额 × 0.5%
```

页面业务解释为：

```text
定价总额 × 5% × 10% = 定价总额 × 0.5%
```

佣金扣除不会从页面展示的“达人佣金”字段中提前扣除，而是在利润计算时单独扣除。

### 3.7 个别达人和外部达人特殊统计规则

#### 3.7.1 特殊规则的维护方式

代码中没有按照达人姓名或 UID 硬编码某个固定公式。个别达人规则来自外部达人台账：

```text
external_talent_registry
```

台账可以为达人维护：

- 所属外部团队；
- 平台和店铺；
- 达人 UID；
- 抖音号和达人名称；
- 商品 ID、商品编码；
- 线上佣金率；
- 线下佣金率；
- 留存比例；
- 链接或渠道码；
- 客单价；
- 备注和启用状态。

只有满足以下条件的台账记录才参与当前抖音订单识别：

```text
platform_type = douyin AND status = 1
```

#### 3.7.2 外部达人匹配顺序

系统识别某笔订单是否属于特殊外部达人时，依次尝试：

```text
1. 店铺 + 达人 UID
2. 店铺 + 抖音号
3. 店铺 + 达人名称/账号名称
4. 如果店铺内未命中，再使用空店铺的全局规则兜底
```

匹配优先级为：

```text
UID > 抖音号 > 达人名称
```

同一个匹配键存在多条记录时，查询按台账 `id` 倒序，当前实现采用最新一条记录。

#### 3.7.3 订单归属分类

订单匹配完成后分为以下类型：

| 类型 | 判断规则 | 当前处理 |
| --- | --- | --- |
| 小店自营 | 没有达人 UID、达人名称和抖音号，或明确匹配店铺账号 | 佣金率展示为 `0%` |
| 内部达人 | 命中内部 `account`，未命中外部达人台账 | 佣金率展示为固定 `5%` |
| 外部达人 | 命中外部达人台账，未命中内部账号 | 使用台账特殊佣金率 |
| 归属冲突 | 同时命中内部账号和外部达人台账 | 标记为“归属冲突”，不自动按普通外部达人结算 |
| 未归类 | 以上规则均未命中 | 不使用特殊达人佣金率 |

> 原始订单 UID 优先用于利润归属。只有订单原本完全没有达人信息，且千川计划能够明确分配时，才允许用千川计划反推达人 UID。

#### 3.7.4 佣金率展示规则

不同类型订单的佣金率展示优先级如下：

```text
小店自营：0%

内部达人：固定 5%

外部达人：
  优先使用台账线上佣金率
  → 线上佣金率为 0 时使用台账线下佣金率
  → 都没有时再尝试精选联盟订单佣金率

归属冲突：
  优先使用台账线上佣金率
  → 没有时按内部达人 5% 展示
```

系统兼容以下佣金率录入方式：

| 台账值 | 解释结果 |
| --- | --- |
| `0.05` | `5%` |
| `5` | `5%` |
| `500` | `5%` |

即：`0～1` 按小数比例处理，`1～100` 按百分数处理，大于 `100` 按万分数处理。

#### 3.7.5 外部达人线下佣金

只有被明确识别为“外部订单”的有效订单才计算线下佣金：

```text
外部达人线下佣金
= 有效订单商品单价
× 商品数量
× 台账线下佣金率
```

不参与线下佣金计算的情况：

- 小店自营订单；
- 内部达人订单；
- 归属冲突订单；
- 未归类订单；
- 无效订单；
- 台账线下佣金率为 `0`。

```text

```

特殊外部达人线下佣金不会改变该页面的佣金和利润。抖音订单页即使计算出线下佣金，当前利润计算仍固定传入线下佣金 `0`，所以线下佣金目前属于独立展示指标，没有真正进入统一实时利润。

### 3.8 李百川与王梅雪的千川借号规则

李百川和王梅雪的规则不属于外部达人台账，也不是按特殊佣金率结算，而是“千川账户临时统计归属”规则。

#### 3.8.1 业务含义

业务场景为：

```text
千川账户原负责人：李百川组
临时使用/统计负责人：王梅雪组
原因：王梅雪临时借用李百川千川账户
```

该规则遵循：

```text
账户资产绑定关系不变
订单原始达人 UID 不变
仅在指定日期范围内改变千川报表的统计负责人
```

因此这不是把李百川的达人订单转给王梅雪，也不是改变两人的达人佣金率，而是希望把借号期间指定千川账户的广告消耗和投放指标统计到王梅雪名下。

#### 3.8.3 规则表字段

借号规则维护在：

```text
qianchuan_advertiser_attribution_rule
```

关键字段为：

```text
advertiser_id          千川广告主 ID
source_trader_id       原负责人，即李百川组
target_trader_id       临时负责人，即王梅雪组
effective_start_date   生效开始日期，包含当天
effective_end_date     生效结束日期，包含当天；空值表示持续有效
reason                 借号原因
status                 0=停用，1=启用
```

同一广告主的多条启用规则不允许日期重叠，同一广告主也不允许配置多个不同的原负责人。

#### 3.8.4 入库时如何改归属

规则命中时，会将千川报表中的以下组织字段改为王梅雪组：

```text
trader_id       → 王梅雪组
company_id      → 王梅雪组所属公司
department_id   → 王梅雪组所属部门
organization_id → 王梅雪组所属公司（仅计划日报）
```

不会修改：

```text
advertiser_id   千川广告主 ID
account_id      内部抖音账号 ID
aweme_id        抖音达人 ID
订单 talent_id  原始订单达人 UID
```

处理的千川报表包括：

| 报表 | 数据表 | 借号归属处理 |
| --- | --- | --- |
| 千川计划日报 | `qianchuan_ad_report` | 修改公司、部门、投手、组织字段 |
| 千川达人日报 | `qianchuan_author_daily_report` | 修改公司、部门、投手字段 |
| 千川乘方日报 | `qianchuan_overall_promotion_daily_report` | 修改公司、部门、投手字段 |
| 千川账户日报 | `qianchuan_advertiser_daily_report` | 不保存组织字段，因此不直接修改 |

新数据拉取时会读取启用规则；系统启动时还会执行一次历史同步，用规则重新处理已经入库的日报。

#### 3.8.5 具体账号匹配优先级

计划日报和达人日报如果已经准确匹配到某个内部抖音账号，实时入库时优先保留该具体账号的组织归属；只有没有准确账号时才使用借号规则作为兜底。

但历史同步会直接按“千川广告主 ID + 生效日期”更新报表组织字段。因此规则启用并完成同步后，借号区间内的相关千川日报理论上统一归到王梅雪组。

乘方日报以千川账户为统计主体，借号规则优先于普通账户映射，命中日期后直接归到王梅雪组。

#### 3.8.6 对财务指标的预期影响

按照业务设计，2026-07-01 至 2026-07-14 期间，上述 4 个账户应表现为：

```text
王梅雪组：增加对应千川广告消耗、计划指标、成交指标
李百川组：不再统计对应借出账户的千川消耗
```

订单收入、商品成本和达人佣金仍按订单原始达人/账号归属，不应随千川借号自动转移。

因此如果需要计算借号后的人员利润，合理口径应当是：

```text
李百川利润
= 李百川原始订单经营收益
- 李百川未借出的千川消耗

王梅雪利润
= 王梅雪原始订单经营收益
- 王梅雪原有千川消耗
- 借用李百川账户期间产生的千川消耗
```

#### 3.8.7 当前实际生效缺口

目前借号规则尚未完整贯通达人佣金和利润统计：

1. 借号规则主要修改 `qianchuan_ad_report`、`qianchuan_author_daily_report` 和乘方日报中的组织字段；
2. 财务“千川消耗”页面按报表 `trader_id/company_id/department_id` 查询的排行榜和明细，可以体现借号归属；
3. 财务“达人佣金”页面按投手计算广告费时，最终还会根据 `trader_account_relation + account_qianchuan_mapping` 的静态账户关系，去汇总 `qianchuan_advertiser_daily_report.stat_cost`；
4. 静态账号映射仍属于李百川，因此这一步可能重新把借号消耗算回李百川，而不是王梅雪；
5. 订单收入和佣金本身继续按订单原始 UID 归属，借号规则不会将订单收益转给王梅雪；
6. 当前规则已停用。历史同步逻辑会先把首次规则日期之后的数据恢复给原负责人，再仅应用“状态为启用”的规则。由于这 4 条规则现在都是停用状态，数据库日报中的历史王梅雪归属可能被恢复为李百川。

截至 2026-07-20 的数据库核查结果显示，上述 4 个广告主在计划日报和达人日报中的王梅雪组记录数均为 `0`。这说明当前数据库已经没有保留这段借号区间的王梅雪历史归属，和业务希望保留历史借号统计的目标存在差异。

#### 3.8.8 建议的正确处理方式

如果 `status=0` 代表“规则不再继续生效”，但历史日期仍应保留，那么规则处理应调整为：

```text
已结束规则：
  effective_end_date 填实际结束日期
  历史区间继续按 target_trader_id 归属
  结束日期之后恢复 source_trader_id

彻底作废规则：
  才使用 status=0，并恢复历史数据
```

同时需要让达人佣金页的广告费查询直接识别按日期生效的借号规则，或者统一从已经完成组织归属的有效千川消耗视图读取，避免：

```text
千川消耗页面归王梅雪
但达人佣金利润中的广告费又归李百川
```

建议最终统一为：

```text
广告费统计负责人
= 日期范围内有效的借号规则负责人
→ 没有借号规则时，使用静态账号负责人
```

## 4. 利润计算

系统通用利润公式为：

```text
利润
= 定价总额
- 商品货款
- 留底
- 退款成本
- 小店服务费
- 线上佣金扣除
- 线下佣金扣除
- 广告消耗
```

当前抖音财务页面实际参数为：

```text
留底             = 定价总额 × 3%
小店服务费       = 定价总额 × 2%
线上佣金扣除     = 定价总额 × 0.5%
线下佣金扣除     = 0
广告消耗         = 千川账户实扣消耗
退款成本         = 已发货退款订单对应的商品成本
```

因此实际利润公式为：

```text
利润
= 定价总额
- 商品货款
- 定价总额 × 3%
- 已发货退款商品成本
- 定价总额 × 2%
- 定价总额 × 0.5%
- 千川广告消耗
```

化简后：

```text
利润
= 定价总额 × 94.5%
- 商品货款
- 已发货退款商品成本
- 千川广告消耗
```

也可以表示为：

```text
利润
= 达人佣金
- 已发货退款商品成本
- 定价总额 × 0.5%
- 千川广告消耗
```

## 5. 当天与历史数据

达人佣金页面根据查询日期选择不同数据来源：

| 查询范围 | 数据来源 |
| --- | --- |
| 当天 | 实时查询订单和千川消耗 |
| 完整历史日期 | `finance_daily_stats` 日汇总表 |
| 历史日期跨当天 | 历史日汇总 + 当天实时结果 |

定时任务顺序：

```text
04:37  拉取前一天千川数据
06:00  聚合前一天财务账号日汇总
```

财务聚合延后到千川拉取之后，目的是确保广告消耗已经入库。

历史日汇总复用实时页面的账号级计算器，避免历史数据和当天数据采用两套订单归属或利润公式。

组织范围规则：

- 根公司可使用全量抖音统一经营快照；
- 具体公司按本公司及有效子公司的账号统计；
- 部门按本部门及子部门统计；
- 投手按其关联账号统计；
- 千川消耗通过广告主与内部账号、公司、部门、投手的映射关系归属。

## 6. 千川数据拉取链路

### 6.1 总体流程

```text
巨量千川 OAuth 授权
  ↓
获取授权的平台店铺账户
  ↓
解析店铺下的千川广告主 ID
  ↓
按广告主拉取账户、计划、达人和乘方报表
  ↓
保存千川日报数据
  ↓
通过映射表归属到内部账号、公司、部门和投手
  ↓
财务页面聚合广告消耗并计算利润
```

### 6.2 OAuth 与广告主解析

第一步调用：

```text
/open_api/oauth2/advertiser/get/
```

取得授权的平台店铺账户。

第二步将平台账户 ID 作为 `shop_id` 调用：

```text
/open_api/v1.0/qianchuan/shop/advertiser/list/
```

解析真正的千川广告主 ID，并保存到：

```text
qianchuan_token.advertiser_ids
```

Token 管理：

- 每 6 小时检查一次；
- 在过期前 8 小时尝试续期；
- 接口返回 Token 失效时强制续期并重试一次；
- Access Token 和 Refresh Token 都失效时，通知管理员重新授权。

### 6.3 拉取时间与历史回补

自动任务：

```text
任务名：qianchuan_daily_pull
时间：每天 04:37
范围：只拉取前一天
```

历史回补接口：

```text
POST /api/qianchuan-poller/trigger
```

限制：

- 可指定开始日期和结束日期；
- 单次最多拉取 30 个自然日；
- 不允许拉取未来日期；
- 请求提交后由后台异步执行，并记录任务日志。

乘方数据也可以单独拉取：

```text
POST /api/qianchuan-poller/trigger-overall
```

### 6.4 拉取接口和数据表

主要数据包括：

| 数据 | 主要接口/来源 | 保存表 |
| --- | --- | --- |
| 标准推广账户日报 | `qianchuan/report/advertiser/get` | `qianchuan_advertiser_daily_report` |
| 乘方账户日报 | `qianchuan/report/all_promotion/get` | `qianchuan_overall_promotion_daily_report` |
| 全域推广账户数据 | 乘方接口失败或无数据时降级使用 | 合并进入账户日报 |
| 全域计划日报 | 全域推广计划接口 | `qianchuan_ad_report` |
| 标准计划日报 | 全域计划无数据时兜底 | `qianchuan_ad_report` |
| 达人/抖音号日报 | 抖音号维度报表接口 | `qianchuan_author_daily_report` |

系统还会获取授权抖音号列表，用于补充计划数据中缺失的抖音号信息。仅有一个授权抖音号时允许自动补充；存在多个抖音号但无法准确匹配时，不自动填充，避免错误归属。

### 6.5 广告消耗字段

财务利润使用：

```text
qianchuan_advertiser_daily_report.stat_cost
```

该字段表示账户维度的纯广告实扣消耗。

乘方数据中需要区分：

```text
stat_cost_for_roi2
= 纯广告消耗

stat_cost_for_overall_roi2
= 综合成本，可能包含广告消耗、预估达人佣金等
```

利润不能直接将 `stat_cost_for_overall_roi2` 当作广告费，否则可能重复扣除达人佣金成本。

## 7. 千川计划订单归因

千川计划页面层级为：

```text
店铺 → 抖音号 → 商品 → 计划
```

### 7.1 订单匹配键

抖音订单先按以下条件和千川计划日报匹配：

```text
日期 + 店铺 + 商品
```

该归因属于系统内部经营归因，并不是千川官方逐笔订单归因。

### 7.2 多计划分摊

同一店铺、同一商品、同一天存在多个计划时，按广告消耗占比分摊订单经营数据：

```text
计划分摊比例
= 当前计划广告消耗 ÷ 同组全部计划广告消耗
```

然后计算：

```text
计划有效订单数 = 同组有效订单数 × 计划分摊比例
计划商品数量   = 同组商品数量 × 计划分摊比例
计划销售额     = 同组销售额 × 计划分摊比例
计划商品成本   = 同组商品成本 × 计划分摊比例
计划佣金       = 同组佣金 × 计划分摊比例
```

如果同组总消耗为 `0`，则按计划数量平均分摊：

```text
计划分摊比例 = 1 ÷ 同组计划数
```

由于使用比例分摊，计划层级的订单数可能出现小数。

## 8. 千川计划利润

### 8.1 计划佣金

```text
计划佣金
= 计划销售额
- 计划商品成本
- 计划销售额 × 3%
- 计划销售额 × 2%
```

即：

```text
计划佣金 = 计划销售额 × 95% - 计划商品成本
```

### 8.2 计划明细利润

```text
计划利润
= 计划佣金
- 计划广告消耗
- 计划销售额 × 0.5%
```

展开后：

```text
计划利润
= 计划销售额 × 94.5%
- 计划商品成本
- 计划广告消耗
```

当前计划明细利润没有扣除已发货退款商品成本。

### 8.3 顶部总利润

当千川计划页面没有任何关键词、商品、店铺、账户、广告主或抖音号筛选时，顶部汇总使用统一抖音经营快照：

```text
顶部总利润
= 总销售额
- 总商品成本
- 3% 留底
- 已发货退款商品成本
- 2% 小店服务费
- 0.5% 佣金扣除
- 千川账户实扣消耗
```

有筛选条件时，顶部改为汇总当前筛选节点，不再覆盖为统一全量抖音快照。

## 9. 公式汇总

| 指标 | 当前公式 |
| --- | --- |
| 定价总额 | `Σ（有效订单商品单价 × 商品数量）` |
| 商品货款 | `Σ（商品基础成本价 × 有效订单商品数量）` |
| 留底 | `定价总额 × 3%` |
| 小店服务费 | `抖音定价总额 × 2%` |
| 达人佣金 | `定价总额 - 商品货款 - 留底 - 小店服务费` |
| 达人佣金化简 | `定价总额 × 95% - 商品货款` |
| 佣金扣除 | `定价总额 × 0.5%` |
| 退款成本 | `已发货退款订单对应的商品成本` |
| 广告消耗 | `千川账户日报 stat_cost` |
| 统一利润 | `达人佣金 - 退款成本 - 0.5%佣金扣除 - 广告消耗` |
| 统一利润化简 | `定价总额 × 94.5% - 商品货款 - 退款成本 - 广告消耗` |
| 计划分摊比例 | `计划消耗 ÷ 同组全部计划消耗` |
| 计划利润 | `计划销售额 × 94.5% - 计划商品成本 - 计划广告消耗` |
| 外部达人线下佣金 | `外部达人有效订单销售额 × 台账线下佣金率`，当前仅订单页展示 |

## 10. 已知口径差异与风险

### 10.1 “达人佣金”不是实际结算佣金

当前达人佣金没有读取实际结算账单，也没有应用达人线上/线下佣金率，而是固定采用：

```text
销售额 - 商品成本 - 3%留底 - 2%服务费
```

页面名称可能使使用者误认为这是实际应付或已结算达人佣金。

### 10.2 计划明细利润未扣退款成本

统一顶部利润会扣除已发货退款商品成本，但店铺、达人、商品、计划节点利润没有扣除退款成本。因此存在退款时：

```text
各计划利润之和 ≠ 顶部统一总利润
```

### 10.3 筛选前后顶部利润口径变化

无筛选时，顶部使用统一抖音经营快照；有筛选时，顶部汇总当前节点数据。筛选结果不会包含统一退款成本扣除逻辑。

### 10.4 商品成本缺失会虚增利润

未匹配到 `goods.base_price` 的订单成本按 `0` 计算，会造成：

- 商品货款偏低；
- 达人佣金偏高；
- 利润偏高。

需要重点关注页面中的成本匹配订单数，并完善商品编码与基础成本价。

### 10.5 仓库仍保留旧版佣金接口

仓库内仍存在旧版 `/api/org/commission-stats` 组织佣金统计逻辑，其有效订单、服务费等口径与当前财务页面不完全一致。

当前财务管理前端实际使用：

```text
/finance/commission-stats
/finance/commission-children
```

建议后续废弃旧接口或增加明确标识，避免其他功能误调用。

### 10.6 个别达人规则尚未完整落地

外部达人台账已经具备商品、链接、线上费率、线下费率和留存比例等字段，但当前实现仍有以下缺口：

1. 财务管理达人佣金汇总没有使用特殊线上/线下佣金率；
2. 财务统一利润没有扣除外部达人线下佣金；
3. 留存比例、链接/渠道码和客单价没有参与任何计算；
4. 台账备注中的专属链接、后缀、野生达人等自然语言规则不会被自动执行；
5. 虽然台账可以按商品维护多条费率，当前外部达人匹配没有使用订单商品 ID 或商品编码；
6. 同一店铺、同一达人存在多条商品规则时，当前可能直接采用最新记录的费率，而不是订单对应商品的费率；
7. 同时命中内部账号和外部台账时会标记“归属冲突”，该类订单不会计入外部达人线下佣金。

如果财务管理需要按个别达人真实结算，建议先确定正式规则优先级，例如：

```text
店铺 + UID + 商品 + 链接
→ 店铺 + UID + 商品
→ 店铺 + UID
→ 全局 UID
→ 精选联盟实际佣金率
→ 默认规则
```

并明确“线上佣金、线下佣金、留存”是相加、互斥还是条件选择，再接入统一佣金和利润快照。

### 10.7 李百川、王梅雪借号历史归属可能丢失

李百川组借给王梅雪组的 4 个千川账户已经配置了 `2026-07-01～2026-07-14` 的结束日期，但规则同时被设置为停用。当前历史同步只重新应用启用规则，因此停用后会把借号区间恢复到原负责人。

这会造成两个问题：

- 历史千川消耗无法继续反映当时真实的借号使用人；
- 千川消耗页面与达人佣金利润可能采用不同负责人，导致人员利润不一致。

在调整代码前，不应将当前报表中的李百川/王梅雪历史数据直接视为借号口径已经正确落地。
